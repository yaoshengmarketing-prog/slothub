## 1. 文件目的與邊界

本文件把兩個已完成並部署的 Pilot 整理成可執行的判斷規則，協助後續逐篇決定是否需要 Knowledge Diagram、該採哪一種結構，以及最低品質門檻。

本規則不代表所有 Guide 都應加入圖解，也不授權新圖解、文章改寫、Schema、template、CSS、驗證程式或網站功能修改。每一篇實作仍須獨立人工核准。

共同前提：

- Editorial Reading 繼續作為所有 Guide 的閱讀骨架。
- Knowledge Diagram 是文章內的可選知識模組，不是固定 Hero。
- 圖解必須縮短理解路徑，不能只為統一外觀。
- 圖解文字由 Guide Markdown 擁有；元件、CSS 與測試不得成為第二份正文。
- 現有兩個 Pilot 分別證明共用樣式可承接直線與循環，不代表已核准所有圖型。

## 2. 什麼內容適合 Knowledge Diagram

至少符合下列一項，而且圖解確實比短段落或清單更快說清關係時，才值得進入人工圖解審查：

1. 有三個以上必須依序理解的步驟。
2. 流程會回到較早步驟，而且停止條件對理解不可省略。
3. 同一輸入會依明確條件分成不同結果。
4. 一個數值必須經過標籤、單位、適用範圍與證據層級等多層判讀。
5. 兩個容易被當成同義詞的概念，需要以結構明確分開。
6. 只掃數字或功能名稱時，很容易得到與正文相反的結論。

通過准入判斷後，還要同時確認：

- 正文已完整說明圖解內容。
- 精確規則與例外已有核准來源。
- 圖解能用一句話說出唯一教學任務。
- CSS 停用後，原生 HTML 讀序仍能表達完整關係。

### 2.1 已驗證案例

| Guide | 唯一教學任務 | 圖型 | 為何適合 |
| --- | --- | --- | --- |
| Bonus Buy | 買的是進入 Feature 的入口，不是固定結果 | 三步直線 | `Cost → Entry → Outcome` 有真實先後次序，並能阻止「支付成本等於購買獲利」的誤讀。 |

## 3. 哪些內容不應加入圖解

下列情況應維持一般文章排版、清單或表格：

- 一到兩句已能完整回答，沒有順序、循環、分支或多層判讀。
- 使用者主要任務是快速查詞，而不是理解流程。
- 正文尚未具備足夠內容或第一方來源，圖解會比文章更完整。
- 只能把正文句子切成數張卡片，沒有新增可理解的結構。
- 需要假造機率曲線、遊戲結果、樣本數或產業通用公式才能畫圖。
- 圖片或圖示只負責裝飾，不能協助辨認、理解、比較或操作。
- 概念是並列分類，但現有樣式只能把它錯畫成步驟。
- 必須依靠動畫、箭頭或 JavaScript 才能知道讀序。
- 圖解會把品牌化名稱誤寫成跨廠商通用規則。

圖解缺失時，頁面應自然維持 Editorial Reading，不保留空容器或額外間距。

## 4. 如何選擇圖解類型

### 4.1 直線型 Sequence

適用條件：

- 每一步有不可顛倒的先後次序。
- 完成最後一步後，流程不會回到前一步。
- 沒有需要同等強調的替代結果。

使用 `<ol>` 表達順序。桌機可多欄，手機必須依 DOM 順序單欄排列。

已驗證案例：Bonus Buy 的 `Cost → Entry → Outcome`。

不適用：純分類、詞彙定義、循環或多條結果。

### 4.2 循環型 Cycle

適用條件：

- 流程完成判定後，可能回到較早步驟。
- 繼續條件與停止條件都能由正文明確支持。
- 省略停止條件會造成「必然一直發生」的誤解。

主流程仍以 `<ol>` 表達；循環後的結果以可讀清單列出「繼續」與「停止」。視覺箭頭只能作輔助，不得成為唯一語意來源。

已驗證案例：Cascading 的四步循環；再次得獎回到第 2 步，沒有得獎或符合停止條件則結束。

### 4.3 分支型 Branch／Decision

適用條件：

- 讀者必須先核對一組條件，才能進入不同判定結果。
- 每條結果均有清楚、非推測的文字條件。
- 分支不是把未知值硬分成好／壞，也不暗示推薦。

共同檢查步驟可使用 `<ol>`；結果使用 `<ul>` 或定義清楚的分支清單。每條分支必須寫出「依什麼條件」和「得到什麼閱讀結論」。

建議下一個案例：Max Win 的「可作統一比較值／只保留原廠標籤與來源」。

### 4.4 不能硬套現有三種圖型的內容

賠付機制、Wild／Scatter／Free Spins／Jackpot 等並列概念，較接近比較型或角色型圖解。若沒有自然順序、循環或判定分支，不得為了沿用現有卡片而假造步驟。這類圖型須另案定義與人工核准。

## 5. 圖解位置

預設位置：

1. H1、description lead 與「從這裡開始」維持現行結構。
2. 第一段正文先用一般文字交代核心答案與限制。
3. Knowledge Diagram 放在首段之後、第一個 H2 之前。
4. 第一個 H2 開始完整解釋、案例與例外。

只有當圖解專門承接文章中段的局部概念時，才可放在對應 H2／H3 之後；不得把中段模組移成裝飾性首屏 Hero。

同一篇原則上只放一個主要 Knowledge Diagram。若一篇需要多張才能成立，應先檢查文章是否混合太多內容責任。

## 6. 圖解文案規則

### 6.1 圖解標題

- 用一句話說清圖解要回答的問題或結論。
- 不重複文章 H1。
- 不使用「必勝、提高勝率、最強、最值得」等推銷語言。
- 讀者只讀標題，也不應得到過度承諾。

### 6.2 摘要

- 一到兩句交代圖解適用範圍與最重要限制。
- 若不同廠商或模式可能不同，直接在摘要提示逐款核對。
- 不把完整例外清單塞入摘要；細節留在正文。

### 6.3 步驟

每一步只做一件事：

- 短 term：例如「成本、入口、結果」或「開始、更新、補位、判定」。
- 動作標題：使用可辨識的動詞或狀態，不用抽象口號。
- 一句說明：只保留理解該步驟不可少的條件。

步驟文字不應逐段複製正文，也不在卡片內放完整遊戲案例、長數據表或來源清單。

### 6.4 分支

- 先寫共同判定點，再列出各條結果。
- 每條分支都要有名稱、條件與後續方向。
- 循環分支必須說明回到哪一步。
- 停止分支必須保留停止或未知條件，不得只顯示成功路徑。
- 顏色不得把任一分支暗示為「比較會贏」或建議選擇。

## 7. 禁止的誤導表達

圖解與正文都不得：

- 保證獲利、回本、指定獎項或較高單次勝率。
- 把 Feature 入口寫成必然觸發某一結果。
- 把高價格、高倍數或更多回合寫成保證較高回報。
- 把 Multiplier 放進所有 Cascading 的必然流程。
- 把連鎖中的再次判定寫成免費增加一次付費旋轉。
- 把 Bonus、單一符號或局部 Feature 上限當成整局 Max Win。
- 把動態最大 Ways 顯示成每局固定 Ways。
- 把原廠品牌名稱當成所有廠商完全相同的規則。
- 把未知資料顯示成 0、沒有或失敗。
- 用向上箭頭、彩金、金幣爆發、成功徽章等視覺暗示結果或獲利。

## 8. 圖解與正文的分工

Knowledge Diagram 負責：

- 讓讀者快速看懂順序、循環、分支或判讀層次。
- 提醒一個最重要的限制或誤讀風險。
- 提供可回到正文核對的結構骨架。

正文負責：

- 定義、原廠術語、不同廠商差異與例外。
- 精確數值、單位、成立條件與第一方來源。
- 具名遊戲案例。
- 版本、市場與資料缺口。

圖解不能新增正文沒有的規則，也不能只把整段正文切碎後換成卡片。最簡單的檢查方式是：移除圖解後，文章仍完整；保留圖解單獨閱讀時，核心關係仍正確但不冒充完整規則。

## 9. 語意、響應式與降級最低要求

### 9.1 HTML 與讀序

- 使用 `<figure>` 與唯一 `figcaption`。
- 順序流程使用 `<ol>`；非順序結果使用 `<ul>`。
- `aria-labelledby` 必須指向存在且唯一的 caption id。
- 可見文案全部存在 Guide Markdown。
- 裝飾性編號或箭頭不可成為螢幕閱讀器唯一可用的關係說明。
- 不應加入不必要的 tab stop；靜態圖解靠正確結構閱讀。

### 9.2 手機與 reflow

- 桌機可多欄；390px、320px 與 200% zoom 必須依 DOM 順序單欄或自然換行。
- 步驟、分支與中英混排不得裁切、重疊或使用 `word-break: break-all`。
- 圖解與頁面都不得產生整頁水平溢位。
- 圖解較長可以向下延伸，不能為了塞入單屏而縮小到難以閱讀。

### 9.3 無 JavaScript、CSS 停用與純文字

- 核心內容必須存在於靜態 HTML，不依賴 JavaScript 插入。
- CSS 停用後仍保留 caption、ordered list、branch list 與完整文字。
- 純文字複製時，標題、步驟、回到位置與停止條件順序可理解。

### 9.4 Print 與 forced colors

- 列印時移除背景與陰影，但保留結構、邊界與讀序。
- 避免在合理範圍內把同一 figure 拆頁；若內容過長，正文仍須可讀。
- forced colors 下使用系統色維持邊框、編號與分支辨識。
- 不以顏色作為區分「繼續／停止」或其他分支的唯一方法。

## 10. 共用樣式與資料責任

後續圖解應沿用現有：

- `.guide-knowledge-diagram`
- `.guide-knowledge-diagram__steps`
- `.guide-knowledge-diagram__decision`
- `.guide-knowledge-diagram__branches`
- sequence／cycle 等描述結構的 modifier

規則：

- class 名稱不得包含 Guide slug。
- 不在 CSS、元件或驗證程式硬編文章文案。
- 不建立 concept → diagram、Guide → diagram 或 taxonomy 的第二份 mapping。
- 不為每篇建立專屬元件；只有新圖型確實需要不同語意 contract 時，才另案評估最小共用擴充。
- CSS 使用 `auto-fit` 或可伸縮 grid，不寫死三步、四步或單一 overflow 數量。
- 驗證程式可檢查結構、所有者、位置、讀序和禁止型態，但不成為文案來源。
- 圖解缺失時不渲染任何 placeholder。

目前 Markdown 內語意化 HTML 加單一 Guide-only CSS 已足夠，不需要修改 Guide Schema、template 或 Markdown pipeline。

## 12. 下一個最小 Pilot 建議

### 12.1 建議 Guide

`slot-max-win-explained`

### 12.2 建議圖型

判讀流程＋結果分支：

```text
原廠原始標籤
  → 投注或數值基準是否清楚
  → 描述整局上限，還是單一符號／Feature／Bonus 局部上限
  → 可作統一比較值
     或
     只保留原廠標籤、條件與來源
```

這不是遊戲結果流程，不能把「可作統一值」畫成成功路徑，也不能把另一條分支畫成錯誤。兩條分支只代表不同資料可比性。

### 12.3 為何現在值得做

- 文章已有 11 個 H2、完整案例與第一方來源，圖解不會取代正文。
- 使用者容易把 `Max Win`、`Max Exposure`、`Winning Ratio`、coins 或單一符號上限當成同質數字。
- 新 Pilot 可驗證「資料判讀分支型」，補足目前只有直線與循環的圖型覆蓋。
- 可沿用現有 decision／branch 樣式；不需要建立 Guide 專屬元件或資料 mapping。

### 12.4 RTP 是否仍合理

RTP 仍是合理而且重要的未來圖解主題，但**不是目前最穩妥的下一篇**。它必須先以獨立內容任務補齊：

- 理論比例適用的時間與樣本尺度。
- 單次結果不能用來驗證 RTP。
- 多版本 RTP 的來源與呈現差異。
- 不同版本、營運設定與讀者可見數值的邊界。

補強完成後，RTP 適合使用「長期大量結果／單次結果」尺度對照型，而不是步驟型；不得用假造 spin 結果或上升圖暗示回報。

## 13. 未來 Skill 可採用與不可自動化的規則

### 13.1 可成為固定檢查

- 是否符合圖解准入條件。
- 正文是否已存在且完整。
- 圖型選擇是否符合順序、循環或分支事實。
- figure／figcaption／ol／ul／id 結構是否合法。
- 圖解是否位於核准段落位置。
- 是否存在靜態 HTML、手機單欄、print 與 forced-colors 規則。
- 是否出現 slug-specific CSS、第二份 mapping、固定步驟數或禁止詞句。
- 是否影響沒有圖解的 Guide。

### 13.2 必須人工審查

- 圖解是否真的比正文更容易理解。
- 摘要是否準確保留廠商、版本與停止條件差異。
- 是否產生獲利、成功或推薦暗示。
- 文案是否把品牌名稱誤升格成通用公式。
- 手機高度、資訊密度、中英混排與視覺節奏。
- 新圖型是否值得擴充共用 CSS contract。
- 一篇文章是否應加入圖解，以及是否已具備足夠內容厚度。

因此目前已具備足夠規則，能讓 Agent 進行逐篇候選稽核與本機檢查；但每一篇的題材選擇、文案、圖型與發布仍須人工核准。
